
- Finance intake queue statuses: filing a bank/"other" document sets "filed", confirming a payment match sets "paid"; "approved" is only for purchase approvals. Multi-document PDFs become one queue item per document sharing the source file (split_of_file_url + page range) and each is read with a page-only instruction (pdf-lib can't parse many bank PDFs). Claude reads first; Gemini is a second reader only for SECOND_READER_TYPES. Why: clear status semantics and lower AI cost.
- Email intake reads only the Google connection signed in as the address in finance_intake_settings (findMailboxKey in gmail-intake.ts; no connection → 503, never another mailbox), query "has:attachment newer_than:14d"; finance_sender_rules (address or domain) run before any AI read — ignore wins, process forces AI "ignored" into triage. Why: docs@ is a dedicated finance mailbox; personal inboxes are never read for finance.
- Duplicates (src/lib/finance/intake-duplicates.server.ts) run before any AI read: same file SHA-256 → status "duplicate" without a model call; then NIF+normalised number+year, bank account/date/amount/ref or statement period; probable matches block approval until resolved, decisions kept per ordered pair in finance_duplicate_decisions. Why: nothing is ever created twice and a person decides unclear cases once.
- Learning (src/lib/finance/intake-learning.server.ts): active finance_intake_instructions go to Claude as "Regras do estúdio", supplier defaults come from the last 2+ agreeing approved items, up to 5 finance_intake_corrections as examples; what was applied is stored on the queue row (applied_learning). Why: rules beat model judgement and every document shows why.
- Suspected duplicate purchases (src/lib/finance/purchase-duplicates.functions.ts, admin + finance): same supplier + normalised number + year, or same supplier + total ±0.01 + date ±5 days without a number match; voiding sets status cancelled with void_reason/voided_duplicate_of/voided_by/voided_at (never deleted), 'not duplicate' is stored per pair in finance_duplicate_decisions. Why: duplicates must stay traceable and decisions remembered.
- Notes ("Guardar nota") are saved as finance_intake_instructions with scope document / recipient_nif / supplier_nif / sender / global, the document is re-read at once, and similar pending items are re-read only after the person confirms the preview. Why: rules act immediately but never silently on other documents.
- Recipient rule (src/lib/finance/recipient-rule.server.ts) runs on every read: PSA = recipient NIF equals company_nif, or no NIF and a name matching pm_invoice_settings.company_name_variants; a different NIF or a clearly different name → status "removed" (Eliminados, restorable, keep_despite_recipient after restore), unreadable/missing or model disagreement → Triagem; documents PSA issued, forced types and nao_financeiro are exempt; duplicates win. Removed items are purged after 30 days by the gmail-intake hook (file only if unshared) and logged. Manual deletion needs a reason (recorded as a 'removal' correction) and may save an instruction with action 'remove' (deterministic, never sent to the model). Auto-removal requires the non-PSA recipient name/NIF to be stored on the item (bare street addresses are not names); otherwise Triagem. finance_other_entities is kept (possible future forwarding exceptions) but has no UI; the outra_entidade type is retired. Why: only PSA's documents may stay and every removal must be explainable and reversible.
- Drive copies of filed bank documents (src/lib/finance/bank-drive-filing.server.ts copyQueueItemToDrive) record drive_copy_status/file id/link/error on the queue row; failures keep the Hub status "filed" and retry at 30 min, 2 h, 12 h via the gmail-intake poller, then wait for a manual retry. All GOOGLE_DRIVE_* folder settings go through parseDriveFolderId (src/lib/google-drive-folder.ts). Why: a pasted Drive link must work and a failed copy must never be silent.
- Incoming payments (src/lib/finance/recebimentos.server.ts / .functions.ts): comprovativo_pagamento, recibo and nota_lancamento store payer/beneficiary/description and payment_direction (PSA beneficiary = incoming, PSA payer = outgoing). Incoming proofs join a finance_recebimentos row (amount ±0.01, date ±5 days, same payer or client) or create a suggested one; client = companies by NIF, then company_ibans (learned only on confirm, never PSA's own IBANs), then name; bank lines and open pm_invoices / inflow schedule items / issued client invoices (combinations up to 3) are suggestions only. Only confirmRecebimento marks things paid, reconciles bank lines (never re-reconciles) and files the proofs. Why: nothing is marked paid without a person confirming, and every payment keeps all its evidence together.

- Multi-entity: our own legal entities live in finance_entities (never the CRM companies table). The 32 company-scoped finance tables carry entity_id with NO default; RLS adds fin_row_visible(entity_id) = has_entity_access AND entity = current_finance_entity() (the user's switcher choice in finance_entity_preferences), child tables check the parent via fin_entity_of. Service-role writes must set entity_id explicitly (intake = PSA_ENTITY_ID from src/lib/finance/entity.ts) or the fin_require_entity trigger fails; signed-in writes take the current entity; project/HR tables (pm_invoices, pm_payment_schedule_items, pm_suppliers, benefit_expenses) are PSA and keep their owner/project branches unscoped. supabaseAdmin reads must filter by entity themselves. Why: separate entities share all code and no screen can mix two.
- Entity routing (Stage 3): company identity comes only from loadEntityIdentity(entity_id) / loadActiveIdentities() in recipient-rule.server.ts (that entity's pm_invoice_settings row with project_id null + IBANs of its own bank_accounts) — never "the" settings row. Intake runs routeEntity against every active entity: one match → that entity, none → PSA's rule (Eliminados/Triagem), several → PSA Triagem with entity_conflict_ids ("Duas entidades"); bank documents follow their account's entity; kept/forced items stay where they are. Every supabaseAdmin read on entity tables filters by the item's entity; confirmRecebimento refuses any linked row of another entity. historical/purge_exempt rows are never purged. Why: service-role code bypasses RLS, so entity separation must be explicit there.
- Cross-entity guard (migration 0040): triggers fin_guard_entity_refs / fin_guard_btc_entity refuse (23514) any insert/update whose reference (classification, bank account, document, recebimento, bank lines, invoices, schedule items, statement import/period) points to another entity; checked only when the reference or entity changes. When moving rows between entities, clear their references first. Why: entity separation must hold even for service-role writes.
- People outside PSA (members of other entities only; is_psa_staff() false, archived collaborators included) see only Finance: useModuleAccess allows only "finance" and the app layout sends other links to /finance. They may add companies (created_by = themselves) and edit one only while company_psa_referenced() is false; deleting companies stays PSA-staff only. Why: shared clients/suppliers are PSA data.
- Each entity has its own classification tree (Pedra Rioja codes PR.*); the AI prompt lists the channel entity's codes plus every other active entity's categories (buildCatalogText), and the code is resolved only in the routed entity's catalogue. "Find by NIF": fin_find_company_by_nif returns only id/name/NIF; fin_link_company_to_entity adds a finance_entity_companies row (visible via fin_company_visible) and never grants edit rights. Why: entities never share codes, and members of other entities never see PSA supplier history.
- PSA tree (migration 20261008190000): only active categories are chosen (fin_category_only_trg on documents, bank classifications, lines, rules, benefit expenses); old→new codes in finance_classification_code_map, every move in classification_remap_log; group-level records wait in "Por reclassificar" (fin_reclass_list / fin_accept_reclass); policy order = record spending_policy_override → finance_entity_companies.spending_policy_default → category; HR benefit expenses get a Pessoal category via zz_benefit_expense_classify. Why: one category per record, traceable remaps, per-entity supplier defaults.
- Supplier tax numbers (migration 20261009090000): companies.nif holds valid Portuguese NIFs only (trigger companies_tax_guard: check digit + fin_nif_is_placeholder, non-PT numbers move to foreign_tax_id); platform suppliers (is_platform: Uber, Bolt, taxis, Amazon) need no NIF and the real issuer is stored per document in issuer_name/issuer_nif/issuer_tax_country/issuer_foreign_tax_id (intake: matchPlatformSupplier + issuerTaxColumns in src/lib/finance/platforms.ts); duplicate checks prefer the issuer number; nothing matches on an invalid/empty NIF; tax field changes are logged in tax_number_change_log (reason via set_config('fin.change_reason')). Why: platforms have many legal issuers and fake NIFs must never identify a supplier.
- Payment cards (migrations 20261009100000/100100): payment_cards per entity stores only last4 (never a full number); "paid with" is paid_from_card_id XOR paid_from_account_id on documents/review queue/expense items. Card comes from a printed card field via fin_card_by_last4 (unique match in the record's entity only, never guessed; unknown → "Cartão desconhecido …1234"), or on bank matching from fin_paid_from_of_bank_line (bank_refs, then the account's single credit card, then the account); supplier's usual card is a suggestion only. fin_set_created_by stamps created_by on hand-made finance rows. Why: card data stays minimal and every payment source is traceable.
- Personal-card decisions act in the database (trigger fd_personal_card_decision): "personal" cancels the document (void_reason Pessoal) and moves its inbox items to Eliminados (removed_source personal_card, normal 30-day purge); "psa_paid_by_holder" requires a personal card and creates a finance_holder_reimbursements row (owed until marked repaid); switching back undoes either; every decision and status change goes to finance_personal_card_log. Inactive cards only explain past lines of their own archived account (fin_paid_from_of_bank_line); new matching uses active cards only. Why: the choice must change the books, and money owed to a person must never be forgotten.
- Single "Confirmar" (migrations 20261009130000–130200): the review screen calls confirmQueueItem → fin_confirm_queue_item (one transaction: edits, counterparty by NIF/platform/create, classification, paid with, finalise; each step in finance_intake_confirm_log). Rules live once in fin_queue_blockers (mirrored client-side in review-queue.tsx); repeats in fin_queue_is_repeat; "Por pagar" = queue.marked_unpaid. The old step functions stay for internal use. Why: nothing is half-approved and the screen and database agree on what blocks.
- "Pago com" autofill (migration 20261009140000): queue trigger zz_fdrq_fill_paid_with pre-fills from fin_supplier_habit_paid_with (last 3 non-cancelled docs of the supplier in the entity, all the same active card/account) as source "habitual", and at confirm (supplier approval step) from fin_queue_bank_paid_with (exactly one outgoing line, ±0.01, ±5 days, not already paying a document; card by a unique last4/device on the line, else fin_paid_from_of_bank_line) as "bank"; fin_queue_blockers counts a bank match as satisfied. "Pago — meio por identificar" = paid_method_unknown (set via fin_queue_set_paid_unknown before confirm), copied to the document; fin_payment_set_paid_from fills it at reconciliation. Why: the Hub fills payment method from evidence, never guesses.
- Guided "Pago com" (migration 20261010190000): review card asks method → holder → card, or method → account; payment_method + paid_by_holder on queue and documents (set via fin_queue_set_paid_how before confirm), card/account nullable; any payment_method with no card/account sets paid_method_unknown (confirmable, listed after 30 days). Receipt digits (extracted_card_last4, card field only) fill the card via fin_card_by_last4 as "card_print" and show read-only; bank fills at confirm and reconciliation pass fin_paid_with_fits (holder only among their cards, transfer/debit only bank accounts, cash never). The old method/last-4 Detalhes fields are gone. Why: one source for how something was paid, and partial knowledge narrows matching instead of blocking.

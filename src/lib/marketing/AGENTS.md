# Marketing module rules
- Finished reels use private write-once upload sessions, shared bounded MP4 validation and advisory-locked invoker marketing_finish_reel; preview resolution uses JPEG covers, publication resolves the video. Exception to original retention: owner-authorized service-only daily cleanup through the existing secret-gated publishing job removes only full-size videos after confirmed publication plus 30 days, with persistent claims/bytes and draft purge metadata, preserving every other asset and all editorial/publication evidence. Purged reels resolve to covers and cannot be reused without a new upload. Reel cover/feed choices extend only reel hashes; purge metadata stays outside hashes. Why: offline originals permit bounded video storage without losing evidence or enabling duplicate publication.
- Posting-time maps share best-times.ts and a security-invoker batched RPC; use latest per-media snapshots within 90 days, Lisbon hourly buckets, sample shrinkage and format-specific evidence. Optional follower activity is probed daily by the existing insights job, with unsupported/empty responses stored as missing, never zero; no AI or Meta writes. Why: calendar suggestions and Insights must agree without inventing confidence or changing publication rules.
- Reapproval eligibility reads the RLS-scoped canonical approval-state view; stale unsent drafts return through marketing_prepare_reapproval to existing editorial guards and approval records. Only a fresh normal approval clears the active failure after archiving it in the attempt log; send/lock/counter evidence is never reset. Why: content changes must be recoverable without duplicate publication or lost history.
- Clearance sources use security-invoker views; source-change triggers batch-refresh suggested/pending_approval/approved/scheduled/failed metadata only, never canonical content or approval/scheduling fields. Capture flag dismissals use a curator-checked RPC and append-only history, excluding matching flags without editing originals or replacing named-client confirmation. Why: live advisory warnings must not invalidate editorial decisions.
- Post language resolves run override, then platform override, then project default; stored draft language is effective-content metadata outside the unchanged canonical hash. Manual translation returns editor content only and saves through existing content invalidation; AI originals stay immutable. Why: project preferences guide new copy without rewriting history or altering approval/publication protections.
- Story burn-in is browser Canvas JPEG rendering with theme fonts and safe zones, stored write-once at draft/story-render/canonical-hash/index.jpg through caller-authorized functions and a service-only compare-and-set manifest RPC; previews and publisher consume these exact ordered files, and sticker consent lives in hashed final frames. Why: reviewed pixels cannot change under an approval or publication lock; manual/unresolved stickers never auto-publish.

- Meta connection verification uses the authenticated meta-connection-check.functions.ts RPC and a server-only Graph batch helper; roles are checked through the caller-scoped has_role RPC before reading secrets, and settings writes retain caller RLS. The first failed call's Meta code/subcode/type/fbtrace_id and a redacted message are saved in marketing_settings.meta_error_* and shown on the card. Why: tokens stay out of browser bundles, URLs, logs and tables, while admin verification cannot be bypassed.
- Every server-side Meta/media fetch uses redirect "manual" and rejects any 3xx as an error (never followed); thrown fetch errors are stored as name + redacted message. Why: the Workers runtime throws on redirect "error", and following a redirect could forward the token.

- Marketing module: captures in marketing_captures (original fields immutable via trigger) + files in private marketing-assets bucket at {capture_id}/...; always served via signed URLs. Capture/photo/Story originals remain retained; only confirmed published reel videos have the documented owner-authorized retention exception above. Why: originals are evidence and assets may need client clearance.
- Marketing email intake: ideas@ read via GOOGLE_MAIL_API_KEY_3 in src/routes/api/public/hooks/marketing-intake.ts; hook secret lives only in Vault (marketing_intake_secret, checked by service-role-only marketing_intake_secret_matches). Why: no secret values in migrations or env duplicates.
- Marketing project profiles: one shared profile for live and standalone portfolio projects; marketing_key is the immutable Marketing identity, captures reference profile_id (project_id remains a real optional operational FK), and draft project_id resolves the Marketing key. Directory reads preserve caller RLS; linking changes only the optional operational relation; AI identities pass safeProfileForAI, excluding protected internal names/client/aliases. Standalone profiles never create pm_projects rows. Why: portfolio history remains Marketing-only and survives later linkage.
- Portfolio identity function patches must assert all expected signatures, reject old operational-key patterns and require the replacement patterns at migration time; clearance source labels fall back to profile internal_name. Why: unmatched text replacements must fail rather than silently bypass portfolio warnings.
- Marketing profile publication rules: public rules (name_rule, public_description, clearance, rules_notes) curator-only enforced by trigger; effective clearance = strictest of capture and project via marketing_effective_clearance / strictestClearance. Why: publication rules set once per project and can never be loosened by a single photo.
- Marketing AI enrichment: src/lib/marketing/enrich.server.ts (Claude via gateway /v1/messages, model in ENRICH_MODEL) run by /api/public/hooks/marketing-enrich (Vault secret marketing_enrich_secret) and reenrichCapture; fills only NULL curation fields, never clearance/curator_notes; story additions go to marketing_project_story_suggestions and are accepted via marketing_accept_story_suggestion (append-only). Why: the AI suggests, people decide.
- Marketing post suggestions: src/lib/marketing/posts.server.ts (POSTS_MODEL, Claude via /v1/messages) run by generatePostSuggestions; drafts in marketing_post_drafts keep ai_copy immutable (trigger), edits in final_copy; readiness and name rules re-checked in code; publishing marks captures used via AFTER UPDATE trigger; readiness is set only by marketing_recheck_draft_readiness (tx-local flag) and re-checked at approval; marketing_post_requests.focus_profile_id narrows candidates to one profile (all confirmed library media, up to 60) and drafts.brief_item records which brief item an idea answers; no image is reused across ideas of one run; story frames may open with one kind "text" preview frame (no asset, not in asset_ids); single-capture runs give one story set for format_hint story (no posts) and at most one for auto. Why: the AI's original stays auditable for a later learning pass.
- Marketing nudges: marketing_nudges (architect may only answer/dismiss own pending unexpired nudge, enforced by marketing_nudges_guard); answers go through submitNudgeAnswer (src/lib/marketing/nudges.functions.ts), which checks ownership then writes story suggestions (source=architect_answer), voice to private marketing-voice/{nudge_id}/, and notifications with the service role; architects answer at /nudges/$nudgeId via server fns so no capture policies change. Why: architects get a single answer screen without wider marketing access. Email replies tagged [Q-xxxxxxxx] (marketing_nudges.reply_tag) are read by marketing-intake and applied via applyNudgeAnswer (nudges.server.ts), shared with the Hub; answer_source_message_id prevents double processing. Why: one answer path for every channel.
- Marketing capture deletion: deleteCapture (src/lib/marketing/captures.functions.ts) checks as caller, then service role removes marketing-assets/marketing-voice files, records email source in marketing_email_ignored (reason deleted_capture) and deletes; BEFORE DELETE trigger + mc_delete policy refuse captures in any post draft and non-curators except own new/enriched. Why: deletions must not break intake de-dup or published history.
- Marketing library: press kits (marketing_project_press_kits) + media (marketing_project_media, files at marketing-assets/library/<profile_id>/) per profile; readable by marketing.view/all, writable via marketing_can_brief_profile; caption_ai immutable; draft asset_ids may hold media ids, resolved by resolveDraftImages (draft-images.ts); publish stamps last_used_at; deletion via deleteMedia, blocked while any draft uses it. Why: evergreen approved material is reused, never marked used.
- Marketing actions: marketing_actions (+ marketing_action_files at marketing-assets/actions/<id>/); curators create/edit/cancel, owner+helpers only add outcome notes/files and mark done (marketing_actions_guard); marketing_actions_sync keeps reminders (owner: entity_type marketing_action/id; helpers: marketing_action_support/marketing_action_support_key because reminders are unique per entity) and notifications; outcome files routed by their uploader via routeOutcomeFile. Why: tasks live in My actions until closed with an outcome.
- Marketing capture notes: marketing_capture_notes (voice at marketing-voice/capture-notes/<capture_id>/), writable via marketing_can_note_capture (curator, capture creator, project team); addCaptureNote transcribes, adds a team_note story suggestion and re-runs enrichCapture inline; loadTeamContext (enrich.server.ts) feeds notes + answered nudges to enrichment and to the planner as team_context. Why: the person who knows the story can add it directly.
- Marketing carousel composer: marketing_compositions/_slides/_comments (route /marketing/carousels/$id); slide order is fixed by people and writeComposedPost (compositions.server.ts) only writes copy, inserting one planner idea (request origin 'composer') with asset_ids in slide order (text slides = design_media_id); text-slide designs are marketing_project_media kind 'text_slide', excluded from planner candidates and library lists; sent compositions are read-only by trigger (duplicate for a new version); nudges may target a composition and answers become comments. Why: the curator owns the story, the AI only words it.

- Voice input goes through src/components/marketing/use-voice-recorder.ts: AudioContext created synchronously in the click, "recording" only after real frames, silent clips never sent, failures (no audio) logged to voice_input_failures (admin-read). Why: Safari/Windows silently recorded nothing before.
- Marketing editorial calendar and approvals: scheduled_at uses Lisbon in UI; asset_ids is ordered media. Readiness/clearance are advisory at approve/request/schedule/publish; named-client concerns require explicit hash-bound confirmation on approval, with system-owned warning history on the draft. Approval hashes, content invalidation and publishing locks remain mandatory; AI inputs keep hiding sector/location. Why: human editorial decisions remain auditable without readiness blocking publication.
- Instagram stage 2 uses instagram-publish.server.ts, service-only claim/checkpoint RPCs, private one-hour media URLs, marketing_publish_log and the Vault-gated marketing-publish callback; admin immediate publishing uses the same pipeline. Created containers lock content, send intent is recorded before media_publish, uncertain outcomes stay blocked, feed cache expires after 15 minutes. Facebook is not implemented. Why: protect approval evidence, prevent duplicates and keep credentials server-only.
- Marketing planner Grid view (stage 3a) uses grid-preview.ts for order/time proposals; confirmed dates go through marketing_schedule_instagram, undated order is local only (no column). Why: approval and hash rules stay in the database.
- Instagram comments (stage 3b): read-only sync in instagram-comments.server.ts run by the existing 15-minute marketing-publish job when older than 14 minutes into marketing_ig_comments (service-written, Marketing-read); reply/hide only from authenticated server fns after a person presses Send/Confirm, each logged in marketing_ig_comment_actions, never retried. AI only drafts. Why: no automatic Meta writes and full traceability.
- Instagram insights are read-only daily snapshots (marketing_ig_media_insights / marketing_ig_account_insights) taken by the existing 15-minute publish job when the last snapshot is >23h old; unsupported metrics are skipped per metric and recorded. Claude analysis receives only buildAnalysisInput (aggregates + our captions with @mentions masked) and is saved in marketing_insight_analyses, never acted on. Why: history beyond Meta retention without new cron or personal data leaks.
- Marketing previews use explicit contain transforms (imgproxy auto-orients EXIF), versioned signed-URL/query caches and centred CSS-only crops; publishing resolves originals without preview. Why: preview files must retain the whole photo, not encode a crop.
- Calendar week items use portrait tiles and cached tile-size previews, month items stay compact; drag images use the visible item and clicks retain the quick preview. Why: weekly columns need legible imagery without loading photo originals.
- Capture card thumbnails use versioned sibling paths and batched signing; overwrite backfill regenerates all. The maintenance script alone may use native EXIF-aware encoding when Storage rejects oversized originals; never import native encoders into app/server modules. Why: preserve originals and avoid exceeding the edge memory budget.
- Inbox capture stage is derived, never stored: security-invoker views marketing_capture_draft_links / marketing_capture_stages map drafts (capture_ids or capture asset ids) to New/To curate/In planner/Scheduled/Published, with only Archived manual; "ready" stays in the enum but is not offered. Email text for AI and cards goes through cleanEmailBody (clean-email.ts) while raw_text stays immutable. Why: the Inbox reflects downstream work without writes, and signatures never reach prompts or cards.
- Marketing navigation follows the workflow (Inbox → Planner → Calendar → Published, then a smaller secondary group); Comments and Insights live under /marketing/published/*, old /marketing/comments and /marketing/insights redirect there; PipelineStrip counts reuse the capture-stage view and planner tabOf. Why: one flow, no broken links, and counts match the tabs.
- Planner is a review queue: PLANNER_VISIBLE_TABS (review/rejected/all) with one card per idea newest first; generation form and run history/deletion live in the Generate ideas dialog; ?tab=approved|scheduled redirect to Calendar and ?tab=published to Published with ?highlight=. Readiness is shown as clearance wording only; "approval" means the editorial decision. Why: decided posts belong to later steps while approval rules stay unchanged.
